только с сервера, фильтры превращаются в query-параметры, задачу можно создать,

### 3.1. HTTP-клиент

`buildUrl` и основа `requestJson` перенесены из ПР5 без изменений логики. Добавлено:

- допустимы только `GET`, `POST`, `PATCH`, `DELETE`; метод приводится к верхнему регистру
  (`"patch"` → `PATCH`), иной метод — `TypeError` до сети;
- `GET` с `body` отклоняется `TypeError` до сетевого запроса;
- `Accept: application/json` есть в каждом запросе, а `Content-Type: application/json` и
  `JSON.stringify(body)` — только при наличии тела (у `GET`, `DELETE` и `reset` его нет,
  поэтому нет и лишнего CORS preflight);
- порядок обработки ответа: отказ `fetch` → `network` / `timeout` / `aborted`; не `Response`
  → `invalid-response`; `!response.ok` → `http` со `status`, `code`, `details`, `url`;
  `204` → `null` без вызова `response.json()`; затем `Content-Type` и разбор JSON;
- тайм-аут — `AbortSignal.timeout(timeoutMs)` (по умолчанию 3000 мс), внешний сигнал
  объединяется с ним через `AbortSignal.any`; по тому, какой сигнал сработал, различаются
  `timeout` и `aborted`.

`fetch` вызывается в отдельном `try`, поэтому `ApiError` вида `http`, созданный после
получения ответа, не превращается в `network`.

### 3.2. Доменный API

`createTaskApi(client)` возвращает девять операций; последний аргумент каждой — `{ signal }`:

| Метод | Запрос | Проверка ответа |
|---|---|---|
| `getTasks(filters)` | `GET /tasks?…` | `data` — массив задач по схеме, уникальные id, `meta.total === data.length` |
| `getTaskById(id)` | `GET /tasks/:id` | `data` — задача по схеме |
| `getCategories()` | `GET /categories` | массив категорий, уникальные id, `meta.total` |
| `loadInitialData(filters)` | `GET /tasks` и `GET /categories` через `Promise.all` | обе части по схеме |
| `createTask(draft)` | `POST /tasks`, тело `{ title, priority, categoryId }` | `data` — задача (id назначил сервер) |
| `updateTask(id, changes)` | `PATCH /tasks/:id`, только изменяемые поля | `data` — задача |
| `setTaskCompleted(id, completed)` | `PATCH /tasks/:id`, тело `{ completed }` | `data` — задача |
| `deleteTask(id)` | `DELETE /tasks/:id` | строго `null` (204), иначе `invalid-response` |
| `resetDemoData()` | `POST /debug/reset` без тела | `{ reset: true, total: <целое> }` |

Фильтры (`completed`, `priority`, `categoryId`, `q`) и id задачи проверяются до запроса
(`TypeError`), схема ответа — после (`ApiError` вида `invalid-response`). Модуль не
обращается к DOM и не формирует пользовательских сообщений.

### 3.3. Состояния интерфейса

```text
start / applyFilters / refresh / после мутации
                 │
                 ▼
     loading (aria-busy="true", старый запрос отменён)
                 │
     ┌───────────┼──────────────┬─────────────────────────┐
     ▼           ▼              ▼                         ▼
  ready       empty          error                 отмена / устаревший
 (карточки,  (0 задач,      (сообщение            ответ: ничего не
  «Найдено»)  нет карточек)  messageForError,      меняется, ошибка
                             кнопка повтора)       не показывается
```

- Первая загрузка — `api.loadInitialData` (задачи и категории параллельно). Пока
  категории не получены, и «Повторить загрузку», и смена фильтра снова вызывают
  `loadInitialData`; после этого используется только `api.getTasks`.
- `empty` — успешный ответ без задач, а не ошибка: выводится «По выбранным условиям задач нет.».
- `error` — текст из `messageForError` (например, «Нет соединения с учебным API…»), рядом
  кнопка повтора.

### 3.4. Изменение данных

Все мутации (`submit`, `toggleTask`, `deleteTask`, `resetData`) проходят через одну
внутреннюю функцию `runMutation`:

```text
setMutationPending(true) → запрос к API → notify("…", "success")
  → loadCurrentTasks() — повторный GET с текущими фильтрами → finally: setMutationPending(false)
```

При ошибке — `notify(messageForError(error), "error")`, а блокировка всё равно снимается в
`finally`. Повторный вызов во время выполнения игнорируется, так что двойной щелчок не
создаёт двух запросов.

- **Создание:** `validateTaskDraft` → при ошибках только `showFormErrors`, запрос не
  отправляется; при успехе `createTask(value)`, форма очищается.
- **Редактирование:** `beginEdit(id)` берёт задачу из последнего ответа и заполняет форму;
  отправка вызывает `updateTask(id, { title, priority, categoryId })` — `completed` не
  передаётся и потому не меняется. `cancelEdit` возвращает режим создания.
- **Статус:** `setTaskCompleted(id, !task.completed)`.
- **Удаление:** `deleteTask(id)`; если удалена редактируемая задача, форма сбрасывается.
- **Reset:** `resetDemoData()`, затем повторный GET с текущим фильтром.
- **Серверная валидация:** если API вернул `400 VALIDATION_ERROR`, его `details` выводятся у
  полей формы — клиентская проверка не заменяет серверную.

Локальный массив в контроллере — только снимок последнего ответа; `localStorage` не
используется.

### 3.5. Защита от устаревшего ответа

`loadCurrentTasks` перед каждым запуском:

1. отменяет предыдущий `AbortController` загрузки;
2. увеличивает номер `loadSequence` и запоминает свой номер.

После ответа результат применяется только при совпадении номера с последним. Вторая
проверка нужна потому, что источник может завершиться, не отреагировав на сигнал (так
устроена модульная проверка 27). Отмена при смене фильтра — ожидаемое действие, поэтому
и `aborted`, и отказ устаревшего запроса не выводятся как ошибка.

Подтверждено в браузере: два вызова подряд `applyFilters({ q: "провер" })` и
`applyFilters({ priority: "high" })` — в Network первый запрос
`GET /tasks?q=провер` имеет статус `ERR_ABORTED`, на экране результат второго
`[4, 13, 16, 25, 34]` в состоянии `ready`, сообщения об ошибке нет.

**Разбор падения.** В проверке «Корректная форма создаёт задачу с серверным id» ожидание
записано как `waitFor(() => requireNode(doc, '[data-task-id="35"]'), …)`. Функция
`requireNode` при отсутствии элемента не возвращает `false`, а выбрасывает исключение,
поэтому `waitFor` завершается ошибкой уже при первом, синхронном опросе — сразу после
`requestSubmit()`, когда `POST` ещё в пути. Карточка от сервера не может появиться
синхронно ни в какой реализации, использующей сеть. Файл проверки совпадает с версией в
репозитории курса и не изменялся.

Тот же сценарий выполнен вручную в приложении с правильным ожиданием (опрос через
`document.querySelector` каждые 25 мс): сразу после отправки карточки нет, через 26 мс
появляется `[data-task-id="35"]` с названием «Подключить браузер» (пробелы по краям
убраны), поле названия очищено, «Найдено: 13», сообщение «Задача создана.». То есть
все утверждения этой проверки выполняются; падает только способ ожидания.

| Смена статуса при активном фильтре | Задача исчезает из выборки «В работе» | Фильтр «В работе» + «Средний»: `[19, 28, 35]` → «Отметить выполненной» у `19` → `[28, 35]`, «Найдено: 2», «Задача № 19 выполнена.» |
| Отмена подтверждения удаления | Запрос не отправляется | `confirm` → «Отмена»: новых запросов 0, `28` осталась |
| Кнопка reset | Восстанавливается исходный набор | `[1, 10, 19, 28]` в варианте, у `id = 1` снова исходное название, «Учебные данные восстановлены.» |
| Перезапуск API | Восстанавливается исходный набор | Создана задача `35` (13 задач), API перезапущен, после перезагрузки страницы — 12 задач, `35` нет |

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` обычно не отклоняет Promise при статусе 404 или 500?**
   Сервер доступен и прислал HTTP-ответ — запрос как обмен по сети прошёл успешно.
   Отклонение бывает при сетевой проблеме или отмене, поэтому статус проверяется через `response.ok`.
2. **В каком порядке проверяются `response.ok`, статус 204, `Content-Type` и JSON?**
   Сначала `ok` (иначе `http`-ошибка со статусом), затем `204` → `null`, затем `Content-Type`,
   затем разбор JSON. Так статус `502` с HTML не маскируется ошибкой формата.
3. **Чем `POST` в контракте работы отличается от `PATCH`?**
   `POST /tasks` создаёт новый ресурс, id и `completed` назначает сервер. `PATCH /tasks/:id`
   частично меняет существующую задачу и передаёт только изменяемые поля.
4. **Для чего сервер возвращает 201 и заголовок `Location`?**
   `201 Created` сообщает, что ресурс создан, тело содержит созданную задачу, а `Location` —
   адрес нового ресурса (`/api/tasks/35`).
5. **Почему у ответа 204 не вызывается `response.json()`?**
   У `204 No Content` нет тела; разбор пустой строки завершится `SyntaxError`. Клиент
   возвращает `null` раньше.
6. **Когда браузер отправляет CORS preflight и почему `no-cors` не решает задачу?**
   Перед запросом к другому origin, если метод не простой (`PATCH`, `DELETE`) или есть
   заголовки вроде `Content-Type: application/json`: браузер шлёт `OPTIONS` и проверяет
   разрешения. `no-cors` делает ответ непрозрачным — JSON прочитать нельзя; решение —
   заголовки CORS на сервере.
7. **Чем `empty` отличается от `error`?**
   `empty` — запрос успешен, данных по условиям нет: нормальный результат, без кнопки
   повтора. `error` — запрос не удался, данных нет вовсе: сообщение о причине и повтор.
8. **Почему `localStorage` больше не является источником задач?**
   Данные принадлежат API; локальная копия расходилась бы с сервером и с другими
   вкладками. Массив в контроллере — только снимок последнего ответа.
9. **Зачем повторно загружать список после успешной мутации?**
   Чтобы показать подтверждённое сервером состояние с учётом текущих фильтров: задача
   могла выйти из выборки, сервер мог нормализовать данные или назначить id.
10. **Как возникает гонка двух запросов при быстрой смене фильтра?**
    Оба запроса в пути одновременно, первый может ответить позже второго — без защиты
    старый результат перезапишет новый фильтр.
11. **Почему одного `AbortController` недостаточно?**
    Источник может не отреагировать на сигнал сразу (кэш, тестовый дублёр, уже полученный
    ответ). Номер запуска гарантирует, что применяется только последний результат.
12. **Почему отмена запроса не показывается пользователю как ошибка?**
    Отмену инициировало само приложение при смене фильтра — это управление потоком, а
    не сбой; сообщение ввело бы пользователя в заблуждение.
13. **Что проверяет клиент, а что обязан повторно проверять сервер?**
    Клиент проверяет форму для быстрой обратной связи (название, приоритет, категория из
    справочника). Сервер проверяет всё заново, потому что клиент можно обойти, — его
    `VALIDATION_ERROR` выводится у полей.
14. **Зачем контроллеру зависимость `view`, переданная параметром?**
    Контроллер не обращается к `document` и проверяется в Node.js с объектом-дублёром;
    DOM-адаптер можно заменить, не меняя логику.
15. **Почему серверный текст выводится через `textContent`?**
    Название — недоверенный текст: через `innerHTML` строка `<img onerror=…>` выполнила бы
    код. `textContent` показывает её буквально.

## 7. Вывод

Интерфейс, клиент и API связаны цепочкой с одним направлением ответственности:
`dom-app.js` превращает события в вызовы контроллера, контроллер управляет состоянием и
вызывает `task-api.js`, тот выбирает маршрут и проверяет схему, а `api-client.js` отвечает
за HTTP. Сервер — единственный источник данных: после каждой мутации список заново
запрашивается с текущими фильтрами.

Основные решения: метод и тело добавлены в клиент ПР5 без смешивания ошибок (`fetch` в
отдельном `try`, `204` до разбора JSON, `Content-Type` только с телом); отмена плюс номер
запроса защищают от устаревших ответов, и отмена не показывается как ошибка; блокировка
кнопок снимается в `finally`, поэтому ошибка мутации не оставляет интерфейс заблокированным.

При проверке найден дефект в готовой браузерной проверке создания задачи (раздел 5.2):
ожидание обрывается при первом опросе. Сценарий подтверждён вручную, файл проверки не
менялся.
