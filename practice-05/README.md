## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A B C D E F` | A, B, C — синхронный код (B печатается до первого `await` внутри `async`-функции). D и E — микрозадачи, D зарегистрирована раньше. F — задача таймера, выполняется после всех микрозадач |
| Фактический результат | `A B C D E F` | Совпало с прогнозом |
| Прогноз после добавления своего `Promise.resolve().then(G)` после метки C | `A B C D E G F` | G ставится в очередь микрозадач последней, но всё равно раньше таймера |
| Фактический результат | `A B C D E G F` | Совпало |

Фактический вывод `npm run example:order` после добавления обработчика G:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: собственный обработчик Promise
F: задача таймера
```

- **Синхронный код:** A, B, C. Вызов `demonstrateAwait()` выполняет тело функции синхронно до `await`.
- **Микрозадачи:** D (обработчик `.then`), E (продолжение после `await null`), G (собственный
  обработчик). Порядок совпадает с порядком регистрации: D — до вызова функции, E — внутри
  вызова, G — после C.
- **Таймер `0`:** задержка `0` означает лишь минимальную задержку постановки задачи. Задача
  таймера ждёт, пока закончится текущий синхронный код и опустеет очередь микрозадач.
- **Удаление одного обработчика:** исчезнет только его строка; например, без D останется
  `A B C E G F`. Относительный порядок остальных не меняется, F всё равно последняя.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный API (не изменялся): маршруты, фильтры, ошибки, CORS, отладочные ответы |
| `src/api-client.js` | Транспорт: `ApiError`, `buildUrl`, `createApiClient().requestJson` — URL, `GET`, тайм-аут и отмена, статус, `Content-Type`, JSON; о задачах ничего не знает |
| `src/task-api.js` | Предметный слой: маршруты `/tasks`, `/tasks/:id`, `/categories`, проверка фильтров до запроса, проверка схемы после, `loadInitialData` через `Promise.all` |
| `src/variant.js` | Только данные варианта: `variantNumber = 4`, `variantFilters = { priority: "medium" }` |
| `src/main.js` | Консольный сценарий: создаёт клиент и API, печатает результат и контрольную ошибку `999` |
| `checks/own.checks.js` | Собственные проверки (7 сценариев) с API на временном порту |

`fetchFn` передаётся в `createApiClient`, чтобы модульные проверки подставляли подготовленный
`Response` или ошибку без сети, а зависимость клиента от `fetch` была видна явно.

HTTP-ошибки проверяются отдельно от сетевых, потому что это разные ситуации: при сетевой
ошибке ответа нет вовсе, а при `404`/`503` сервер ответил. Поэтому `fetchFn` вызывается в
собственном `try`, а `ApiError` вида `http` создаётся уже после него и не попадает в
`catch`, где мог бы стать `network`.

JSON после разбора проверяется по контракту, потому что синтаксически верный
`{"data":"не массив"}` или задача с `completed: "false"` всё равно непригодны приложению.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `new URL(baseUrl)`; только `http:`/`https:`, без query и hash, иначе `TypeError`. Краевые `/` у пути базы и `path` убираются, части соединяются одним `/` | Клиентские 01, 04 |
| Кодирование query-параметров | `url.searchParams.set(name, String(value))`; пропускаются только `undefined`, `null`, `""`; `false` и `0` сохраняются; `query` только читается | Клиентские 02, 03, интеграционная 03 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }` в каждом запросе, `method: "GET"` | Клиентская 05 |
| Проверка `response.ok` | Сразу после проверки, что получен `Response`; при `!ok` — `ApiError` `http` с `status`, `code`, `details`, `url` из `payload.error` (если тело JSON), иначе сообщение `HTTP <статус>` | Клиентские 08, 09, 16 |
| Проверка `Content-Type` | Для успешного ответа после обработки `204`; без `application/json` — `invalid-response` | Клиентская 10, интеграционная 11 |
| Разбор JSON | `await response.json()` в `try`; `SyntaxError` → `invalid-response` с `cause`; `204` → `null` без чтения тела | Клиентские 07, 11, интеграционная 10 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` передаётся самому `fetch`; если сработал именно он — `timeout` | Клиентская 14, интеграционная 12 |
| Внешняя отмена | `AbortSignal.any([signal, timeoutSignal])`; если отменён внешний сигнал — `aborted` | Клиентская 15, интеграционная 13 |

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач: `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]`, `meta.total = 12` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи: `[4, 13, 34]` |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `1` Учёба, `2` Проект, `3` Организация |
| `loadInitialData(...)` | `{ tasks, categories, meta }`: задачи по фильтру, все три категории и `meta` из ответа задач |

Правила проверки:

- **фильтры (до запроса):** допустимы только `completed` (boolean), `priority`
  (`low`/`medium`/`high`), `categoryId` (положительное целое), `q` (строка, после `trim` до
  100 символов, пустая не передаётся); иначе `TypeError`, запрос не выполняется;
- **задача:** положительный безопасный целый `id`, непустой `title` до 100 символов после
  `trim`, boolean `completed`, допустимый `priority`, положительный целый `categoryId`;
- **категория:** положительный целый `id`, непустой `name` до 100 символов;
- **коллекция:** `data` — массив, каждый элемент по схеме, `id` не повторяются,
  `meta.total === data.length`;
- любое нарушение схемы ответа — `ApiError` вида `invalid-response`.

## Последовательная и параллельная загрузка

Временный скрипт (в репозиторий не включён): два запроса `/debug/delay?ms=300` через
созданный клиент — сначала двумя последовательными `await`, затем через `Promise.all`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 643.3 | 610.0 | 609.0 | ≈ сумма двух задержек: второй запрос начинается только после первого |
| `Promise.all` | 307.6 | 305.4 | 303.1 | ≈ одна задержка: оба запроса начаты до общего ожидания и ждут одновременно |

`Promise.all` сам не ускоряет запросы: выигрыш появляется потому, что оба Promise созданы
до `await`. В итоговом `loadInitialData` так и сделано, искусственных задержек нет.

## Отладка

Точки останова в `requestJson`: перед вызовом `fetchFn`, на строке `if (!(response instanceof Response))`,
перед `response.json()` и в `catch` сетевого этапа.

| Значение | Успешный `getTaskById(25)` | Ошибочный `getTaskById(999)` |
|---|---|---|
| URL | `http://127.0.0.1:5505/api/tasks/25` | `http://127.0.0.1:5505/api/tasks/999` |
| `response.status` | `200` | `404` |
| `response.ok` | `true` | `false` |
| `Content-Type` | `application/json; charset=utf-8` | `application/json; charset=utf-8` |
| payload | `{ data: { id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 } }` | `{ error: { code: "TASK_NOT_FOUND", message: "Задача с id 999 не найдена.", details: { id: 999 } } }` |
| Итог | задача прошла `isTask` и возвращена | `ApiError { kind: "http", status: 404, code: "TASK_NOT_FOUND", details: { id: 999 } }`; `catch` сетевого этапа не выполнялся |

При остановленном API выполнение останавливалось в `catch` сетевого этапа:
`error` — `TypeError: fetch failed`, ни `signal`, ни сигнал тайм-аута не отменены, поэтому
результат — `kind: "network"`.

## Вывод

Получен переиспользуемый клиент из двух слоёв: `api-client.js` отвечает за транспорт и
единый `ApiError`, `task-api.js` — за маршруты, фильтры и схему данных. Все 18 + 26 + 13
готовых проверок и 7 собственных проходят, вариант 4 даёт `[1, 10, 19, 28]`.

Различия, которые клиент теперь разделяет:

- **ожидание Promise** — переменная содержит Promise, а не данные, пока не выполнен `await`;
- **HTTP-ошибка** (`http`) — сервер ответил, но статус не 2xx: `fetch` при этом не отклоняется,
  поэтому `response.ok` проверяется явно, а `status` и `code` сохраняются;
- **сетевая ошибка** (`network`) — ответа нет вовсе, отклоняется сам `fetch`;
- **неверный ответ** (`invalid-response`) — статус успешный, но не тот `Content-Type`, битый
  JSON или данные не по схеме;
- **тайм-аут** (`timeout`) — сработал собственный `AbortSignal.timeout`;
- **явная отмена** (`aborted`) — отменил вызывающий код.

Главная ошибка, которой удалось избежать, — общий `try` вокруг всего запроса: тогда HTTP-ошибка,
созданная после `fetch`, стала бы `network`. Отдельно учтено, что `if (value)` выбросил бы
`completed: false` из query, и что `Promise.all` ускоряет загрузку только потому, что оба
запроса начаты до ожидания.
