## 1. Цель и результат

Подключить интерфейс задач к учебному серверу. Клиент получает категории и выборку, запрашивает изменения и после ответа перечитывает данные. Изменения хранятся в памяти процесса API до его перезапуска или сброса набора.

## 2. Запуск

Из папки `practice-08` выполнить `npm ci`. В первом терминале запустить `npm run api`, во втором — `npm run dev`. Интерфейс — http://127.0.0.1:5173/, API — http://127.0.0.1:5505/api. Для другого адреса API создать `.env` по образцу `.env.example` и перезапустить Vite.

Проверки — `npm test`. Для просмотра сборки выполнить `npm run build`, затем `npm run preview`, оставив API запущенным.

## 4. Загрузка и изменения

Эффект зависит от стабильной ссылки `api`, четырёх значений фильтров и `revision`. Чтение вызывает `loadInitialData`, который запрашивает список и категории параллельно. При новой загрузке сохраняется последний снимок и сбрасывается ошибка чтения. Cleanup отменяет конкретный GET. Его сигнал проверяется после успеха и в `catch`, поэтому поздний результат не перезапишет состояние. Эффект монтирования устанавливает `mounted.current` в каждом setup и при cleanup отменяет текущую мутацию.

Ссылка `mutation.current` заполняется синхронно перед первым `await`. Она блокирует второй вызов до рендера. Каждая мутация использует отдельный контроллер. Успех операции увеличивает `revision`, и эффект перечитывает список с текущими фильтрами. Ошибка операции оставляет черновик и записывается в `mutationError`. Если запись подтвердилась, а следующий GET упал, форма получает `true`, интерфейс сохраняет уведомление о записи, а ошибка чтения показывается отдельно.

## 7. Контрольные вопросы

1. Эффект выполняет побочное действие после рендера и даёт возможность его отменить.
2. Cleanup выполняется перед повторным setup с новыми зависимостями, при размонтировании и в пробном цикле StrictMode.
3. Callback эффекта может вернуть функцию очистки. Async-функция возвращает Promise, поэтому ожидание вынесено во внутреннюю функцию.
4. Загрузку определяют API, четыре фильтра и `revision`. Снимок обновляется по результату, поэтому включение его в зависимости создало бы повторные чтения.
5. Смена ссылки на API вызывает повтор эффекта. Стабильный объект сохраняет запрос при обычном рендере.
6. Источник может проигнорировать отмену. Проверка сигнала после ожидания отбрасывает его результат.
7. Поздняя ошибка старого запроса может заменить успешно показанный актуальный результат, поэтому в `catch` действует та же проверка.
8. StrictMode пробует последовательность setup → cleanup → setup, чтобы проверить корректность очистки и повторного запуска.
9. Обновление state может ждать рендера. Ref меняется сразу, поэтому второй вызов видит блокировку.
10. `true` подтверждает запись. Отдельное состояние чтения показывает результат обновления списка.
11. После тайм-аута сервер мог уже записать задачу. Повторный POST может создать дубликат.
12. Фильтр меняет только выборку. Запись относится к конкретной задаче и после успеха перечитывает список с актуальными условиями.
13. Отмена прекращает ожидание клиента. Сервер мог уже начать или завершить операцию.
14. `meta.total` — количество совпадений текущего запроса. Общее число получается из выборки без фильтров.
15. Браузер нужен для реального CORS, сетевого ограничения DevTools, фокуса, клавиатуры и проверки собранного интерфейса.

## 8. Вывод

Загрузка и изменения разделены в хуке. Снимок обновляется по подтверждённому чтению, а синхронная блокировка защищает запись от повторной отправки. Для полной проверки нужен запуск штатных тестов и браузерных сценариев.
